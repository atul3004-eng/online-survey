Cookie and header guidance: OWASP session management, security headers.
1. Configure session cookies
Merge this into the existing <session-config> in your application’s WEB-INF/web.xml:
<session-config>
    <session-timeout>30</session-timeout>
    <cookie-config>
        <http-only>true</http-only>
        <secure>true</secure>
    </cookie-config>
    <tracking-mode>COOKIE</tracking-mode>
</session-config>
This configures JSESSIONID; custom cookies need their own flags. Configure SameSite using your application server’s supported settings. Choose it to support your AD login flow—cross-site login callbacks can require different settings.
2. Set response headers
A servlet filter mapped to /*, or your reverse proxy, can add:
Strict-Transport-Security: max-age=31536000
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Send HSTS on HTTPS responses. Add includeSubDomains only after confirming all affected subdomains support HTTPS. If TLS terminates at a proxy, setting HSTS there is usually simplest. OWASP HSTS guidance
3. Implement CSRF protection for JSF
Use a dedicated filter and token helper:
- Generate a cryptographically random token and store it in the session.
- Include it in each state-changing form.
- Ensure PrimeFaces AJAX requests also submit it, including requests using process="@this".
- Compare the submitted token with the session token before processing the action.
- Reject missing or invalid tokens with HTTP 403.
- Keep GET requests free of state changes.
Do not rely solely on SameSite or assume JSF ViewState protects every endpoint. OWASP CSRF guidance
4. Fix XSS at the output point
For ordinary JSF text:
<h:outputText value="#{bean.userInput}" escape="true"/>
For browser-side text, use textContent instead of innerHTML. HTML escaping alone is insufficient when inserting values into JavaScript or URLs; those contexts need appropriate handling. Cookie flags do not fix the underlying XSS issue. OWASP XSS guidance
